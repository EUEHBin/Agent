## 1. 本阶段在解决什么问题

把一个 FastAPI 后端从「能定义表、能查库」搭到「请求进得来、错误统一、响应格式统一」：

| 讲 | 一句话 |
|----|--------|
| 04 ORM | 用 Python 类描述数据库表 |
| 05 数据操作 | 增删改查怎么写、会话怎么提交 |
| 06 数据迁移 | 表结构变更可追踪、可回滚（Alembic） |
| 07 业务逻辑 | API 薄、Service 厚，边界清晰 |
| 08 依赖注入 | 数据库会话等资源由框架注入，不手搓 |
| 09 统一异常处理 | 所有错误一个出口、统一 JSON |
| 10 中间件 | 请求前后统一加工（耗时、跨域、成功响应外壳） |

前端直觉对照：

- ORM / 数据操作 ≈ 数据模型 + 请求封装  
- 业务分层 ≈ 组件里不堆业务，抽到 service  
- DI ≈ 依赖从外面传入，不写死  
- 异常处理 ≈ 全局错误拦截  
- 中间件 ≈ axios 拦截器 / 全局 middleware

## 2. 四层职责（务必分清）

| 层 | 目录 | 职责 |
|----|------|------|
| **model** | `app/model/` | 对数据库：表、列、关系 |
| **schema** | `app/schema/` | 对接口：入参/出参形状（Pydantic） |
| **service** | `app/service/` | 业务规则、拼查询、commit |
| **api** | `app/api/` | 收请求、调 service、决定抛错或返回 |

另外：

| 模块 | 目录 | 职责 |
|------|------|------|
| 数据库接入 | `app/core/database.py` | Engine、连接池、Session、`get_db` |
| 配置 | `app/core/config.py` | 从 `.env` 读 `DB_*` / `WEB_*` |
| 异常 | `app/exception/` | 业务异常类型 + 全局 handler |
| 中间件 | `app/core/middleware/` | 耗时 / CORS / 统一成功响应 |
| 装配入口 | `app/main.py` | 创建 app、挂中间件、挂异常、挂路由 |
| 迁移 | `apps/web-service/migrations/` | Alembic：建表、改表脚本 |

## 3. 库、表、连接：三件不同的事

### 3.1 连上库 ≠ 已有表

1. PostgreSQL 服务在跑（如 localhost:5432）  
2. `.env` 配好 `DB_HOST/PORT/NAME/USER/PASSWORD`  
3. 应用读配置 → 创建 **Engine（带连接池）** → 能进库 `duyi_db`  
4. **表**要另外创建（见下）

### 3.2 表怎么从零到一生成（正规做法 = 迁移）

```text
写 class Product（图纸）
  → make db-migrate（生成迁移文件，含 CREATE TABLE）
  → make db-upgrade（连库执行脚本）
  → 库里出现表 product
```

- 迁移**就是**日常建表/改表方式，不是「额外选修」  
- 手写 SQL / 图形界面建表也能用，但不便协作与回滚  
- `Base.metadata.create_all()` 只适合本地偷懒，无版本历史  

对照文件：`migrations/versions/ee949af06bdb_init.py` 里的 `op.create_table('product', ...)`。

### 3.3 `Product` 和表 `product`

- `Product` = Python **类名**  
- 表名来自 `Base.__tablename__` → `cls.__name__.lower()` → **`product`**  
- Postgres **不会**因为你写了类就自动建表；要靠迁移执行 `CREATE TABLE`

### 3.4 Engine / 连接池 / Session

| 概念 | 是什么 |
|------|--------|
| Engine | 总管：连哪、账号、**连接池** |
| 连接池 | 复用若干条到 Postgres 的真连接，避免每次新建 TCP |
| Session（接口里的 `db`） | **某次请求**借用的工作单元；用来 `execute` / `commit` |

`Depends(get_db)`：每次请求注入一个 Session，用完归还；**不是**每个请求新建一整套连接池。

## 4. 标准例子：`GET /api/products/1`（成功路径）

根路径：`课件/03-Python框架/10. 中间件/duyi-service/apps/web-service/app/`

```text
客户端 GET /api/products/1
  → main.py 已装配好的 app
  → 中间件（进）：response / cors / process_time 各自 await call_next
  → 路由命中 api/products.py :: get_product
  → Depends(get_db) → database.py 产出 Session 作为 db
  → ProductService(db).get_product(1)
  → ORM select(Product) → execute → PostgreSQL 查表 product
  → ProductResponse.model_validate(product)
  → return result（此时还是「裸」业务 JSON）
  → 中间件（出）：加耗时头；response 包装成 {code, data, message}
  → 客户端收到统一成功格式
```

### 4.1 启动时装配（`main.py`，只做一次）

- `FastAPI(...)` 创建应用  
- `register_middleware(app)` → 第 10 节  
- `add_exception_handler(...)` → 第 09 节  
- `include_router(product_router)` → 第 07 节  

### 4.2 你最容易卡的一行（第 08 节）

```python
@router.get("/{product_id}", response_model=ProductResponse)
async def get_product(
    product_id: int,
    db: Annotated[AsyncSession, Depends(get_db)],
):
```

| 片段 | 含义 |
|------|------|
| `product_id: int` | **路径参数**：URL 里的 `1` 转成 int（不是 DI） |
| `db` | 参数名：本次数据库会话 |
| `AsyncSession` | 类型：SQLAlchemy 异步会话 |
| `Depends(get_db)` | **依赖注入**：先执行 `get_db`，把 `yield` 的 session 塞进来 |

依赖注入一句话：函数需要的东西（依赖）不自己创建，由框架在调用前准备好再传入。

### 4.3 `get_db`（`database.py`）

```python
async def get_db():
    session_factory = get_session_factory()
    async with session_factory() as session:
        yield session
# 接口跑完后：退出 async with，关闭 session，连接还回池子
```

连接串形态：`postgresql+asyncpg://user:pass@host:port/dbname`。

### 4.4 查库（`product_service.py`，04 + 05 + 07）

```python
stmt = (
    select(Product)
    .options(selectinload(Product.categories), selectinload(Product.skus))
    .where(Product.id == product_id)
)
result = await self.db.execute(stmt)  # 这时才真正打到数据库
product = result.unique().scalar_one_or_none()
return ProductResponse.model_validate(product)
```

- 拼 `stmt` 时还没发 SQL  
- `execute` 才与数据库交互  
- `selectinload` 通常是：1 条主查询 + 关联表的 `IN (...)` 查询（不是一次巨型乱 JOIN）

### 4.5 `from_attributes=True`（schema）

```python
class ProductResponse(BaseModel):
    ...
    model_config = {"from_attributes": True}
```

查库得到的是 ORM 对象（`product.id` 属性），不是 dict。  
打开后允许 `ProductResponse.model_validate(product)` 从**对象属性**填充模型。  
（Pydantic v1 旧名：`orm_mode`）

### 4.6 中间件 `call_next`（第 10 节）

```python
async def unified_response(request, call_next):
    response = await call_next(request)  # 暂停 → 去跑路由/业务 → 再回来
    # 读 body，包装成 {code, data, message}
    return JSONResponse(...)
```

- 中间件**不发出**客户端请求；请求是客户端打进来的  
- `call_next` = 框架给的「继续往后处理」  
- `await` = 等后面跑完再包装  

### 4.7 失败路径（第 09 节）——和成功不同出口

```text
result is None
  → raise NotFoundException(message="商品不存在")
  → exception/handler/handlers.py :: exception_handler
  → {"code":"...","message":"商品不存在","data":null}
```

| 情况 | 谁生成最终 JSON |
|------|-----------------|
| 成功 | 业务 return → **response 中间件**包外壳 |
| 找不到 / 业务错 | **handlers.py** |
| 参数校验失败 | 同上（`RequestValidationError`） |

## 5. 写操作多记一点

读（get）往往不 `commit`。  
创建/更新通常要 `flush` / `commit`，否则库里看不到数据。  
对照 `ProductService.create_product` 即可。
