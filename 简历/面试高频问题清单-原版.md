## 二、易鑫：贷前管理后台

### 微前端与 Monorepo

### 6. ★★★ MicroApp 的原理是什么？和 qiankun 有什么区别？

**MicroApp 原理：**

- **渲染方式**：借鉴 WebComponent 的思想，基座里写一个自定义元素 `<micro-app name="xxx" url="...">`。MicroApp 用 `fetch` 拉取子应用的 HTML，解析出里面的 JS 和 CSS，处理后插入到这个自定义元素里渲染。
- **JS 沙箱**：默认是 with 沙箱，用 `Proxy` 代理一个假的 `window`，子应用读写全局变量都落在这个代理对象上，不污染真实的 `window`；卸载时清理定时器和事件监听。也支持 iframe 沙箱，隔离更彻底。
- **样式隔离**：给子应用的 CSS 选择器统一加上 `micro-app[name=xxx]` 前缀，让样式只作用于这个子应用内部。
- **元素隔离**：子应用里调用 `document.querySelector` 只会查到自己范围内的元素。
- **通信**：
  - 基座给子应用传数据：`<micro-app :data="...">` 或 `microApp.setData('子应用名', data)`。
  - 子应用接收：`window.microApp.addDataListener(fn)`。
  - 子应用给基座发数据：`window.microApp.dispatch(data)`。
  - 全局通信：`setGlobalData` 和 `addGlobalDataListener`。
- **其他能力**：`preFetch` 预加载子应用资源；`keep-alive` 模式让子应用切走后保留状态，切回来不用重新渲染。

**和 qiankun 的区别：**

| 对比项 | MicroApp | qiankun |
| --- | --- | --- |
| 底层 | 类 WebComponent 的自定义元素 | 基于 single-spa |
| 子应用改造 | 很少，基本只要配置跨域 | 要导出 `bootstrap`、`mount`、`unmount` 生命周期，并把构建产物改成 UMD 格式 |
| 使用方式 | 像用一个组件一样嵌入 | 需要注册子应用和激活规则 |
| 对 Vite 子应用的支持 | 支持较好 | 需要额外插件 |

一句话总结：MicroApp 接入成本更低，qiankun 生态更成熟、用的人更多。

**我们为什么选 MicroApp**：【子应用多、技术栈有差异，希望改造成本低 / 项目搭建时已经定了】。

### 7. ★★ 29 个子应用怎么管理？公共依赖、公共组件怎么共享？

> 目录结构上，`apps` 下面是基座和各个子应用，`packages` 下面是公共包，比如组件库、请求封装、工具函数。子应用通过 pnpm workspace 的 `workspace:*` 引用公共包，改了公共包所有子应用都能立刻用上。
>
> 依赖版本在根目录统一管理，避免出现两个子应用用两个版本的 Vue。每个子应用可以单独启动、单独构建、单独部署，互不影响。
>
> 我补齐多环境配置和整理飞书知识库，也是为了让 29 个子应用的地址、技术栈、业务入口有一份统一的说明。【补充你们实际的目录和工具，比如是否用了 Turborepo】

### 8. ★★ 为什么选 Monorepo？它的缺点是什么？

**优点：**
- 公共代码直接共享，不用发 npm 包、来回升级版本。
- 依赖版本统一，减少同一个库多个版本的问题。
- 改动公共包时，能在一个仓库里直接看到对所有子应用的影响，一次提交就能改完。
- 规范、脚本、CI 配置可以统一。

**缺点：**
- 仓库体积大，克隆和安装慢。
- 全量构建慢，需要做增量构建或缓存。
- 权限粒度粗，不好限制某个人只能改某个子应用。
- 公共包改坏了，影响面很大，所以需要更严格的 Code Review 和测试。

### 9. ★ 子应用之间路由怎么跳转？子应用 404、白屏怎么排查？

**跳转方式：**
- 通过基座跳转：子应用 `dispatch` 一个跳转事件，基座的路由去切换。
- 用 MicroApp 提供的路由 API（`microApp.router.push`），指定子应用名和路径。
- 通用办法：调用 `history.pushState` 后手动派发 `popstate` 事件，让各自的路由感知变化。

**404 排查：**
- 子应用的路由 `base` 有没有配成基座分配给它的前缀。
- 用 history 模式时，服务器（Nginx）有没有配置回退到 `index.html`。
- 子应用静态资源的 `publicPath` 是否正确。

**白屏排查：**
- 先看控制台报错和 Network 面板，看子应用的 HTML、JS 有没有加载成功。
- MicroApp 用 `fetch` 拉子应用资源，子应用服务器必须允许跨域，这是最常见的原因。
- 看是不是某个第三方库和沙箱不兼容（比如直接操作真实 `window`），可以尝试切换 iframe 沙箱。

### 工程化

### 10. ★★★ 主包从 5MB 降到 2MB，具体做了什么？用什么分析的？

> 先用 `rollup-plugin-visualizer` 生成产物分析图，看哪些模块最大。发现主要问题是【比如 ECharts、Element Plus、lodash 全量打进了主包 / 多个大依赖没拆分 / 有重复依赖】。
>
> 做了几件事：
> 1. **拆包**：用 Vite 的 `build.rollupOptions.output.manualChunks`，把 Vue 全家桶、UI 库、图表库分别拆成独立的 chunk。这些库很少变，拆出来后可以长期缓存。
> 2. **按需引入**：UI 组件和图表组件改成按需引入，lodash 换成 lodash-es 让它能被 Tree Shaking。
> 3. **路由懒加载**：页面组件都用 `() => import()` 动态导入，首屏只加载需要的页面。
> 4. **【其他：CDN 外链、去掉重复依赖、压缩图片等】**
>
> 最终主包从 5MB 降到 2MB，【首屏加载时间从 X 秒降到 X 秒】。

### 11. ★★ 多环境构建怎么做的？

> 用 Vite 的 mode 机制。每个子应用下放 `.env.dev`、`.env.test`、`.env.uat`、`.env.production`，里面写接口地址、子应用地址等变量，变量名以 `VITE_` 开头，代码里通过 `import.meta.env.VITE_XXX` 读取。构建命令用 `vite build --mode test` 这样区分环境。
>
> 原来的问题是【部分子应用缺少某些环境的配置，测试环境连到了别的环境的接口 / 地址写死在代码里】，我把所有子应用都补齐了，并且统一了变量命名。

### 12. ★★★ 发布流程改造：为什么这样改？“拦截两次错误合并”具体是什么情况？

> **原来的问题**：开发分支直接合入 main 后发布。这样 main 上同时混着要发布的代码和还在开发的代码；一旦线上有问题要回滚，会把正在开发的功能一起回滚掉，发布也会打断大家的开发。
>
> **改成**：每次上线前，从开发分支拉一个独立的上线分支，只包含这次要发布的内容，在测试环境验证，次日确认没问题后再合入 main。发布和回滚都在上线分支上操作，不影响开发分支。
>
> **两次拦截的例子**：【比如某次有同事把还没测完的功能合进了要上线的分支，在次日验证环节被发现 / 某次合并冲突处理错误，覆盖了别人的代码，在上线分支上验证时发现】。如果按原来的流程，这些代码会直接上线。

**可能追问：和 Git Flow、Trunk Based 有什么区别？hotfix 怎么走？**

- **Git Flow**：有 `main`、`develop`、`feature`、`release`、`hotfix` 多种分支，流程规范但比较重。我们的做法其实接近 Git Flow 里的 `release` 分支思路，但简化了。
- **Trunk Based**：所有人频繁往主干小步提交，靠特性开关和自动化测试保证质量，对测试覆盖率要求很高。
- **hotfix**：从 main（线上版本）拉 hotfix 分支修复，验证后合入 main 发布，同时再合回开发分支，避免下次发布把问题带回来。

### 组件

### 13. ★★★ 通用 CRUD 组件是怎么设计的？

> 核心思路是**配置驱动**。一个列表页通常由搜索区、表格、分页、操作按钮组成，这些都可以用配置描述：

```js
const config = {
  api: { list: getUserList, delete: deleteUser },
  search: [
    { field: 'name', label: '姓名', type: 'input' },
    { field: 'status', label: '状态', type: 'select', options: statusOptions },
  ],
  columns: [
    { prop: 'name', label: '姓名' },
    { prop: 'phone', label: '手机号', mask: 'phone' },
    { prop: 'status', label: '状态', dict: 'status' },
  ],
  actions: ['edit', 'delete'],
}
```

> 组件内部统一处理：调接口、分页、加载状态、重置搜索、删除二次确认、字典翻译、脱敏展示。
>
> **扩展性**：
> - 列和搜索项支持插槽，特殊的单元格可以自定义渲染。
> - 提供钩子，比如请求前处理参数、请求后处理数据。
> - 暴露刷新、获取选中行等方法给父组件调用。
> - 如果某个页面需求实在太特殊，允许不用这个组件，不强行把所有场景都塞进来，否则组件会越来越难维护。
>
> 目前已经在 6 个模块的列表页落地。

### 14. ★★ 脱敏组件怎么做的？前端脱敏安全吗？

> 这里要分清楚：**只在前端脱敏是不安全的**。如果接口返回的是完整的手机号、身份证号，前端只是显示成 `138****1234`，用户打开 Network 面板照样能看到原始数据。
>
> 正确的做法是**后端返回脱敏后的数据**。需要查看完整信息时，调用单独的接口，后端做权限校验并记录查看日志。
>
> 我做的统一脱敏组件，主要解决的是**展示规则统一**：手机号、身份证、银行卡、姓名分别用什么规则展示，“点击查看”的交互怎么做，避免每个页面写一套。【如果你们当时确实只在前端脱敏，可以说：后来也和后端推动了接口层脱敏】

### AI 研发提效

### 15. ★★★ AGENTS.md、Rules、Skill、OpenSpec 分别是什么，有什么区别？

| 名称 | 是什么 | 解决什么问题 |
| --- | --- | --- |
| AGENTS.md | 放在仓库里写给 AI 看的项目说明，Codex、Cursor、Claude Code 等多数工具都会读 | 让 AI 每次都知道项目结构、命令和规矩，比如必须用公共组件、不要直接用 axios |
| Rules | Cursor 自己的规则文件，放在 `.cursor/rules/` 下，可以按文件类型或路径生效 | 作用和 AGENTS.md 类似，但可以更精细，比如只对 `*.vue` 文件生效 |
| Skill | 某一类任务的操作手册，包含步骤、约定和示例 | 让 AI 稳定地完成一类重复任务，比如“按需求生成 CRUD 列表页” |
| OpenSpec | 一套“先写规格再写代码”的工作流 | 改动前先产出提案、方案、任务、验收标准，人确认后再编码；完成后规格留档 |

一句话区分：**AGENTS.md 和 Rules 管“规矩”，Skill 管“某类活怎么干”，OpenSpec 管“一次改动的流程和留档”。**

### 16. ★★★ 同类页面从 4 天缩短到 1 天，是怎么算的？

> 对比的是【标准的列表加详情加编辑页面】这类需求。
>
> 原来 4 天大概花在：读需求和整理字段 0.5 天，写页面骨架和搜索、表格、表单 1.5 天，字段映射、字典、校验 1 天，联调和改 bug 1 天。
>
> 现在：AI 通过 lark-cli 读需求文档，按 Skill 里的约定生成字段映射和页面骨架，我主要做检查、补业务逻辑和联调，整体 1 天左右。
>
> 这个数字是【根据几个同类需求的实际排期对比估算的】，不是所有页面都能达到，业务逻辑特别复杂的页面提升有限。

> 注意：主动说明“适用范围”，比夸大数字更可信。

### 17. ★★★ AI 生成的代码质量怎么保证？出过什么问题？

> 主要靠四层保障：
> 1. **事前约束**：AGENTS.md 和 Rules 里写死规矩，比如必须用公共组件、请求层和脱敏规则，不许改无关文件。
> 2. **小步生成**：用 OpenSpec 把需求拆成小任务，每个任务单独生成和检查，不让 AI 一次改一大片。
> 3. **人工 Review**：AI 生成的代码和人写的一样走 Code Review，我自己先过一遍。
> 4. **验收标准**：规格里写清楚验收条件，完成后逐条核对。
>
> 出过的问题，比如【AI 生成页面时没有用我们的请求封装，直接用了 axios，导致没有统一的错误处理和 token；后来把这条写进了 Rules，之后就没再出现】。我的经验是，AI 犯过的错，要沉淀成规则，而不是每次手动改。

### 19. ★★ lark-cli 读取飞书文档具体怎么用？需求文档写得不清楚时怎么办？

> lark-cli 是飞书的命令行工具，可以用命令把飞书文档内容读出来。AI 在终端里调用它拿到需求文档和 bug 文档的内容，作为上下文来生成开发计划。

### 20. ★ INE AI 报告前端展示有什么难点？

> 【按实际情况回答。如果是流式输出，可以这样讲】
>
> AI 报告是流式返回的。因为请求需要用 POST 并带鉴权头，浏览器原生的 `EventSource` 不支持，所以用 `fetch` 拿到 `response.body`，通过 `ReadableStream` 逐块读取并解析。
>
> 难点有三个：
> 1. **Markdown 实时渲染**：内容是一段段过来的，要边接收边渲染，同时避免频繁全量渲染导致卡顿，所以做了节流。
> 2. **安全**：AI 返回的内容要用 DOMPurify 之类的库过滤后再渲染，防止 XSS。
> 3. **中断和重试**：用户切走页面时用 `AbortController` 取消请求。

## 三、慧策：慧经营 SaaS

### 大数据表格

### 21. ★★★ 大数据表格用的什么方案？为什么不自己写？

> 用的是【具体的库，比如 vxe-table / umy-ui / 其他】。选型时对比了【Element UI 原生表格、某几个虚拟表格库】。Element UI 的表格会把所有行都渲染成 DOM，几千行就明显卡顿。
>
> 选这个库的原因：支持行和列双向虚拟滚动、支持固定列和合并单元格、和 Element UI 风格接近、社区活跃。
>
> 不自己写，是因为虚拟表格里固定列、合并单元格、动态行高、横向虚拟滚动这些细节很多，成熟的库已经解决了，自己写成本高、风险大。我们在它的基础上做了二次封装，统一了配置方式。

### 22. ★★★ 虚拟滚动的原理是什么？

> 核心是**只渲染看得见的部分**。
>
> 1. 外层是固定高度的滚动容器。
> 2. 里面放一个占位元素，高度是“总行数 × 行高”，用来撑出正确的滚动条。
> 3. 监听滚动事件，根据 `scrollTop` 算出当前应该显示第几行到第几行：起始索引是 `Math.floor(scrollTop / 行高)`，结束索引是起始索引加上可视区域能放下的行数。
> 4. 只渲染这些行，再用 `transform: translateY(起始索引 × 行高)` 把它们移到正确的位置。
> 5. 上下各多渲染几行作为缓冲区，避免快速滚动时出现白屏。
>
> 这样不管数据有 1 万行还是 10 万行，DOM 里始终只有几十行。

**追问：**
- **行高不固定怎么办？** 先按预估高度计算，行渲染出来后测量真实高度并缓存，然后修正后面各行的位置。定位起始行时，可以用二分查找加快计算。
- **列也很多怎么办？** 列也做虚拟化，原理一样，按 `scrollLeft` 算出可见的列。
- **固定列怎么处理？** 固定列单独渲染一份，用 `position: sticky` 或独立的层盖在上面，和主体表格同步纵向滚动。

### 23. ★★★ 渲染时间缩短 80%，怎么测的？优化前后各是多少？

> 用 Chrome 的 Performance 面板录制页面从拿到数据到表格渲染完成的过程，同时在代码里用 `performance.now()` 在数据返回和渲染完成（`nextTick` 之后）两个点打点。
>
> 测试数据是【X 行 × X 列】的报表。优化前渲染要【X 秒】，滚动时帧率明显下降；优化后【X 毫秒】，滚动流畅。

> 注意：这里的数字一定要提前确认，面试官很可能追问。

### 24. ★★ 万级单元格的数据，接口一次返回还是分页？前端还做了哪些处理？

> 报表需要整体查看和汇总，所以【一次返回 / 分页加载】。
>
> 前端还做了这些处理：
> 1. **跳过响应式**：Vue2 会给数据的每个属性递归加 getter/setter，几万条数据光这一步就很耗时。对只展示不修改的数据用 `Object.freeze`，Vue2 会跳过它的响应式处理。Vue3 里对应的做法是 `shallowRef` 或 `markRaw`。
> 2. **计算挪出主线程**：汇总、排序等计算量大的逻辑放到 Web Worker，避免卡住页面。
> 3. **分片处理**：数据预处理用 `requestAnimationFrame` 或 `setTimeout` 分批进行，每批处理一部分，不长时间阻塞主线程。

### 其他优化

### 25. ★★ 虚拟滚动下拉框和表格虚拟滚动有什么区别？搜索过滤怎么做？

> 原理一样，都是只渲染可见的选项。区别是下拉框更简单：一般是固定行高、只有一列、没有固定列和合并单元格。
>
> 下拉框的特殊点在于：
> 1. **搜索过滤**：输入时做防抖，过滤后的结果重新计算虚拟列表，并把滚动位置重置到顶部。
> 2. **回显选中项**：选中值可能不在当前可见区域，要能根据值找到对应的选项显示文字；打开下拉框时自动滚动到选中项。
> 3. 选项特别多时，也可以改成远程搜索，由后端分页返回。

### 26. ★★★ 首页白屏是什么原因？怎么定位、怎么解决的？用什么指标衡量？

**衡量指标：**
- FCP（首次内容绘制）：页面第一次出现内容的时间。
- LCP（最大内容绘制）：页面主要内容出现的时间。
- 也可以自己埋点算白屏时间。

用 Lighthouse 和 Performance 面板分析。

**原因：** SPA 应用要先下载并执行完 JS 才能渲染页面。如果首包太大、同步加载的资源太多，用户就会长时间看到白屏。

**解决方案：**
1. **路由懒加载**：页面按需加载，首屏只加载首页的代码。
2. **按需引入**：UI 库、图表库只引入用到的组件。
3. **Gzip 压缩**：构建时生成 `.gz` 文件，或在 Nginx 开启 Gzip，传输体积能小 60%～70%。
4. **CDN**：静态资源放 CDN，加快下载速度；Vue 等公共库也可以走 CDN 外链。
5. **骨架屏或加载动画**：在 `index.html` 里先放一个 loading，降低用户对白屏的感知。

> 结果：【白屏时间从 X 秒降到 X 秒，打包体积从 X 降到 X】。

### 大文件上传

### 27. ★★★ 大文件上传的完整流程是什么？

1. **切片**：用 `file.slice(start, end)` 把文件切成固定大小的分片，比如每片 5MB。
2. **计算文件 hash**：用 `spark-md5` 根据文件内容算出唯一标识。大文件计算很慢，所以放到 **Web Worker** 里做，不卡页面。也可以用“抽样 hash”（取文件头、尾和中间几段来算），速度快很多，但有极小概率重复。
3. **秒传和断点续传**：上传前先用 hash 问服务端，这个文件的情况如何：
   - 已经完整存在：直接提示上传成功，这就是**秒传**。
   - 传过一部分：服务端返回已上传的分片编号，前端只传剩下的，这就是**断点续传**。
4. **并发上传**：分片不能一次全发出去（浏览器对同一域名的并发连接数有限制，也会压垮服务器），所以限制同时最多上传 3～6 个，完成一个再补一个。
5. **失败重试**：单个分片失败后自动重试几次，仍然失败再提示用户。
6. **合并**：所有分片上传完成后，调用合并接口，服务端按顺序把分片合成完整文件，并校验 hash。
7. **进度**：每个分片通过 `onUploadProgress` 上报已上传的字节数，汇总后除以文件总大小，得到整体进度。

### 28. ★★ 手写一个并发控制函数。

```js
// tasks 是返回 Promise 的函数数组，limit 是最大并发数
async function runWithLimit(tasks, limit) {
  const results = []
  let index = 0

  async function worker() {
    while (index < tasks.length) {
      const current = index++
      try {
        results[current] = await tasks[current]()
      } catch (err) {
        results[current] = err
      }
    }
  }

  const workers = Array.from({ length: Math.min(limit, tasks.length) }, worker)
  await Promise.all(workers)
  return results
}

// 使用：最多同时上传 3 个分片
// await runWithLimit(chunks.map(chunk => () => uploadChunk(chunk)), 3)
```

> 讲解思路：启动 `limit` 个“工人”，每个工人循环从任务队列里取下一个任务执行，执行完再取，直到取完。结果按原顺序放进 `results`。因为 JS 是单线程的，`index++` 不会有并发问题。

### 29. ★ 上传进度怎么算？暂停和恢复怎么做？

- **进度**：每个分片请求用 axios 的 `onUploadProgress` 拿到这个分片已上传的字节数 `loaded`。整体进度是“已完成分片的总大小 + 正在上传分片的 loaded 之和”除以文件总大小。
- **暂停**：给每个请求传一个 `AbortController` 的 `signal`，暂停时调用 `controller.abort()` 取消所有正在进行的请求。
- **恢复**：重新走一遍“问服务端哪些分片已上传”的流程，只上传剩余的分片，也就是复用断点续传的逻辑。

### 业务

### 30. ★★★ 慧经营的业务讲一下：数据从哪来，商家用它解决什么问题？

> **用户**：在多个平台开店的电商商家，比如同时在京东、淘宝、抖音、快手开店。
>
> **痛点**：每个平台都有自己的后台，订单、费用、结算规则都不一样。商家想知道“这个月到底赚了多少钱、哪个店铺哪个商品赚钱”，要从各个平台导出数据手工汇总，又慢又容易错。
>
> **数据来源**：一部分是公司旺店通 ERP 里已有的订单、商品、成本数据；另一部分通过各平台的开放接口拉取订单、退款、平台费用等。
>
> **我们做的**：把多平台数据整合起来，提供订单汇总、记账、销售跟踪、利润报表和经营分析。
>
> **利润怎么算**：大致是“销售收入 − 退款 − 商品成本 − 平台扣点和佣金 − 运费 − 推广费 − 其他费用”。难点是各平台的费用口径不同、退款和结算有时间差，所以要支持用户自定义利润表项。
>
> 我负责的运营分析、经营分析和直播利润分析，就是在这些数据上做多维度的分析，占产品销售额 50% 以上。

### 31. ★★ 利润表自定义计算指标是怎么实现的？公式怎么解析和计算？

> 用户可以自定义指标，比如“毛利 = 销售额 − 商品成本”。
>
> **实现思路**：
> 1. **公式编辑**：用户通过选择已有指标和运算符来组合公式，而不是随便输入文字，从源头减少错误。
> 2. **公式解析**：不用 `eval`，因为它有安全风险，而且无法校验。做法是把公式拆成数字、指标、运算符、括号等单元，转换成后缀表达式（逆波兰表达式）再计算；也可以用 `expr-eval` 这类成熟的库。
> 3. **依赖关系**：指标之间会互相引用，要按依赖顺序计算，并检测循环引用（A 依赖 B，B 又依赖 A）。
> 4. **精度**：金额计算不能直接用 JS 浮点数，`0.1 + 0.2` 不等于 `0.3`。要么统一按“分”换算成整数计算，要么用 `decimal.js` 这类精度库。
>
> 【说明你们实际是前端计算还是后端计算，前端主要负责配置和展示】

### 32. ★★ 埋点自定义指令怎么写的？曝光埋点怎么做？上报怎么保证不丢？

**点击埋点指令：**

```js
// 用法：<button v-track="{ event: 'export_click', page: 'profit' }">导出</button>
const track = {
  mounted(el, binding) {
    el.__trackHandler = () => report(binding.value)
    el.addEventListener('click', el.__trackHandler)
  },
  unmounted(el) {
    el.removeEventListener('click', el.__trackHandler)
  },
}
```

> Vue2 里钩子名是 `inserted` 和 `unbind`。

**曝光埋点**：用 `IntersectionObserver` 监听元素进入可视区域，进入时上报一次，然后取消监听，避免重复上报。

**保证上报不丢：**
- 用 `navigator.sendBeacon` 发送。页面关闭或跳转时，它也能可靠地把数据发出去，普通的 ajax 请求可能会被取消。
- 批量上报：先存入队列，攒够一定数量或定时上报，减少请求数。
- 失败的数据存到 `localStorage`，下次进入页面再补发。

## 四、慧策：管理后台 / 小程序 / BI

### 34. ★★★ 菜单、按钮、路由、数据四级权限分别怎么实现？

1. **菜单权限**：登录后请求当前用户的权限数据，根据它生成侧边栏菜单，没有权限的菜单不显示。
2. **路由权限**：前端只预先注册登录页、404 等公共路由。业务路由根据权限数据，用 `router.addRoute` 动态注册。这样用户在地址栏直接输入没权限的地址，也会进 404。同时在 `router.beforeEach` 里做登录校验。
3. **按钮权限**：写一个 `v-permission` 指令，传入按钮的权限码，用户没有这个权限就把按钮元素从页面上移除。
4. **数据权限**：比如“只能看自己店铺的数据”，主要由**后端**在查询时过滤，前端只负责传参和控制展示。

**追问：前端权限能防住越权吗？** 不能。前端权限只是“不显示”，用户可以直接调接口绕过。真正的权限校验必须在后端做，前端权限是为了用户体验。

### 35. ★★ 多版本控制是什么意思？不同版本的功能差异怎么配置？

> SaaS 产品通常分不同版本卖给租户，比如基础版、专业版、旗舰版，不同版本能用的功能不一样。
>
> 实现上，每个功能点（菜单、按钮）有一个功能码；每个版本配置一组功能码；租户购买了哪个版本，就拥有哪组功能。最终用户的权限 = 租户版本的功能 ∩ 用户角色的权限。
>
> 管理后台提供给测试、产品和运营配置版本和租户，不需要改代码就能调整某个版本包含哪些功能。

### 36. ★★★ 小程序为什么从原生重构成 uni-app？遇到了哪些坑？

**重构原因：**
- 原生小程序的写法和团队主力技术栈 Vue 不一样，维护成本高。
- uni-app 用 Vue 语法，团队里其他人也能参与开发。
- 可以复用 Web 端的部分逻辑和数据协议。
- 以后如果要扩展到其他平台的小程序或 H5，一套代码就能支持。

**遇到的坑：**
- **平台差异**：部分 API 和组件在不同平台表现不一样，要用条件编译（`#ifdef MP-WEIXIN`）分别处理。
- **包体积**：uni-app 会打入运行时代码，体积比原生大，需要分包。
- **性能**：数据更新最终会调用小程序的 `setData`，数据量大时要避免一次更新整个大对象。
- **图表**：ECharts 要换成适配小程序的版本。
- 【补充你实际遇到的】

### 37. ★★ 小程序包大小限制怎么处理？

> 微信小程序主包不能超过 2MB，所有分包加起来不超过 20MB（以微信官方最新规定为准）。
>
> 处理办法：
> 1. **分包**：首页和公共页面放主包，其他功能按模块拆成分包。
> 2. **分包预下载**：配置 `preloadRule`，进入某个页面时提前下载用户可能要去的分包。
> 3. **图片等静态资源放 CDN**，不打进包里。
> 4. 清理没用的代码和依赖，图表库用按需构建的精简版。

### 38. ★★ 你写的几个兼容问题具体怎么解决的？

- **键盘遮挡输入框**：`input` 组件默认 `adjust-position` 为 `true`，键盘弹起时页面会上推。但在固定在底部的输入框、弹窗里会出问题。这时关闭 `adjust-position`，监听 `bindkeyboardheightchange` 拿到键盘高度，手动调整输入区域的位置；也可以用 `cursor-spacing` 设置光标和键盘的距离。
- **安全区适配**：iPhone 底部有横条，固定在底部的按钮会被挡住。用 `padding-bottom: env(safe-area-inset-bottom)` 留出空间；老版本 iOS 要写 `constant(safe-area-inset-bottom)` 做兼容。
- **图表渲染**：小程序里 ECharts 要用适配的版本，比如 `echarts-for-weixin`，或者 uni-app 生态里的图表组件。canvas 是原生组件，层级比普通元素高，会盖住弹窗。用新版 `type="2d"` 的 canvas 支持同层渲染，就能解决层级问题。图表数据量大时要做抽样，避免卡顿。

### 39. ★★★ “减少 70% 后端开发和对接时间”怎么算的？表格配置协议长什么样？

> **背景**：慧经营里有大量报表，每个报表原来都要后端单独写接口、前端单独对接字段。
>
> **做法**：我们约定了一套统一的表格数据协议，后端按协议返回“列定义 + 数据”，前端用一个通用组件渲染，PC 端和小程序都复用这一套。

```json
{
  "columns": [
    { "key": "shopName", "title": "店铺", "type": "text", "fixed": "left" },
    { "key": "sales", "title": "销售额", "type": "money", "sortable": true, "summary": "sum" },
    { "key": "profitRate", "title": "利润率", "type": "percent" }
  ],
  "rows": [
    { "shopName": "京东旗舰店", "sales": 128000, "profitRate": 0.23 }
```

### 41. ★ BI 的拖拽配置、图表联动是怎么实现的？

### 43. ★★★ 单据流转怎么做？状态多了以后代码怎么维护？

> 采购、入库、出库这类单据有很多状态，比如“草稿 → 待审核 → 已审核 → 已入库”，还有“驳回”“作废”。不同状态下能做的操作也不一样。
>
> 如果在每个按钮上写 `if (status === 1 || status === 3)`，状态一多就很难维护。所以我用**状态机的思路**，把“状态和允许的操作”做成一张配置表：

```js
const ORDER_FLOW = {
  draft:    { label: '草稿',   actions: ['edit', 'submit', 'delete'] },
  pending:  { label: '待审核', actions: ['approve', 'reject'] },
  approved: { label: '已审核', actions: ['stockIn', 'void'] },
  rejected: { label: '已驳回', actions: ['edit', 'submit'] },
  stocked:  { label: '已入库', actions: [] },
}

const canDo = (status, action) => ORDER_FLOW[status]?.actions.includes(action)
```

> 页面上的按钮根据当前状态和用户权限共同决定是否显示。新增状态时只需要改配置。
>
> 前端只控制展示，**真正的状态变更校验必须在后端**，防止并发操作或绕过前端直接调接口。比如两个人同时审核同一张单，后端要保证只有一个成功。

### 44. ★★ 复杂表单（批量录入、商品选择）怎么做性能和校验？

- **商品选择**：商品很多时用远程搜索加分页，选择弹窗支持多选，已选商品单独展示，可以删除。
- **批量录入**：表格形式的可编辑表单，每行是一个商品，填数量、单价等。行数多时用虚拟滚动。支持从 Excel 粘贴：监听 `paste` 事件，解析剪贴板里的制表符分隔文本，批量填入。
- **校验**：
  - 单个字段失焦时校验，比如数量必须大于 0。
  - 跨字段和跨行校验，比如同一商品不能重复。
  - 提交前全量校验，定位并滚动到第一个出错的位置。
  - 输入时的实时计算（比如小计）做防抖，避免每输入一个字都重算整个表格。

### 45. ★★ Android 原生和内嵌 Web 怎么通信？有什么安全问题？

**Web 调用原生：**
- 原生通过 `webView.addJavascriptInterface(对象, "名称")` 把一个 Java 对象注入到网页，网页里用 `window.名称.方法()` 调用。Android 4.2 以后，只有加了 `@JavascriptInterface` 注解的方法才能被 JS 调用。
- 或者 URL 拦截：网页跳转一个自定义协议的地址，比如 `jsbridge://getUserInfo?callback=cb1`，原生在 `shouldOverrideUrlLoading` 里拦截并解析。
- 也可以用 `prompt` 拦截（`onJsPrompt`）。

**原生调用 Web：**
- 用 `webView.evaluateJavascript("window.onNativeCallback(...)", 回调)`，可以拿到返回值。

**安全问题：**
- Android 4.2 以前的 `addJavascriptInterface` 有严重漏洞，网页可以通过反射执行任意代码，所以必须加注解，并且设置最低版本要求。
- 只对**白名单域名**开放 JSBridge，防止 WebView 被跳转到恶意页面后调用原生能力。
- 敏感能力（比如获取用户信息、支付）要做额外校验。

### 47. ★★ iBeacon 定位的原理是什么？

> iBeacon 是一种低功耗蓝牙设备，会持续广播自己的唯一标识（UUID、Major、Minor）。手机扫描到信号后，能拿到信号强度 RSSI。
>
> **测距**：信号强度随距离衰减，常用的经验公式是：

```text
距离 = 10 ^ ((A - RSSI) / (10 × n))
```

> A 是距离 1 米时的信号强度，n 是环境衰减系数，需要现场标定。
>
> **定位**：
> - **三边定位**：知道手机到三个已知位置的 iBeacon 的距离，以每个 iBeacon 为圆心、距离为半径画圆，三个圆的交点就是手机的位置。实际中有误差，所以用最小二乘法求最可能的位置。
> - **指纹定位**：事先在场地各点采集信号强度作为“指纹”库，定位时用当前信号去库里匹配最相似的点。
>
> **难点**：RSSI 波动很大，人体遮挡、多径反射都会影响，所以要做滤波，比如去掉异常值后求均值，或者用卡尔曼滤波平滑；还可以结合手机的加速度传感器做步行推算，让定位更稳定。
>
> 【补充你实际用了哪种方案，在会展中心布了多少个 iBeacon，精度达到多少米】

## 七、技能区的八股

### Vue

### 49. ★★★ Vue2 和 Vue3 的响应式原理有什么区别？

**Vue2：`Object.defineProperty`**
- 初始化时递归遍历数据的每个属性，用 `defineProperty` 给它加上 getter 和 setter。
- getter 里收集依赖（谁用到了这个属性），setter 里通知依赖更新。

**Vue2 的问题：**
- **新增和删除属性检测不到**：因为只有初始化时存在的属性才被处理，所以需要 `Vue.set` 和 `Vue.delete`。
- **数组下标和长度的修改检测不到**：Vue2 是通过重写 `push`、`pop`、`splice` 等 7 个数组方法来实现数组响应式的。
- **初始化性能差**：一开始就要递归处理所有数据，数据量大时很慢。

**Vue3：`Proxy`**
- 用 `Proxy` 代理整个对象，可以拦截读取、设置、新增、删除、`in` 操作符等各种操作。
- 新增属性、删除属性、数组下标修改都能检测到，不再需要 `Vue.set`。
- **懒代理**：只有访问到嵌套对象时，才对它做代理，初始化更快。
- 依赖收集用 `WeakMap → Map → Set` 的结构保存“哪个对象的哪个属性被哪些副作用函数用到”。

### 50. ★★★ Vue 的 Diff 算法？Vue2 和 Vue3 有什么区别？`key` 的作用？

**共同前提：**
- 只比较同一层级的节点，不跨层级比较，复杂度从 O(n³) 降到 O(n)。
- 标签名不同直接替换，标签名相同才进一步比较属性和子节点。
- Diff 的难点主要在于新旧两组子节点的比较。

**Vue2：双端比较**

用四个指针分别指向旧子节点的头和尾、新子节点的头和尾，每轮按顺序尝试四种比较：
1. 旧头 vs 新头
2. 旧尾 vs 新尾
3. 旧头 vs 新尾（匹配上说明节点被移到了后面）
4. 旧尾 vs 新头（匹配上说明节点被移到了前面）

四种都没匹配上，就用新节点的 key 去旧节点里查找，找到就移动，找不到就新建。最后多余的旧节点删除，剩下的新节点新增。

**Vue3：预处理 + 最长递增子序列**
1. 先从头部开始比较，相同的跳过；再从尾部开始比较，相同的跳过。
2. 如果只剩新增或只剩删除，直接处理。
3. 中间乱序的部分：建立新节点 key 到位置的映射，算出每个新节点在旧列表里的位置，然后求这个位置数组的**最长递增子序列**。在最长递增子序列里的节点不用移动，只移动其他节点。这样能让 DOM 移动次数最少。

另外 Vue3 在编译阶段做了优化：给动态节点打标记（PatchFlag），把动态节点收集起来（Block Tree），更新时只比较动态部分，静态内容直接跳过。

**`key` 的作用：**
- 让 Diff 能准确判断新旧节点是不是同一个，从而复用节点而不是重新创建。
- **不要用数组下标做 key**：如果在列表中间插入或删除，后面所有元素的下标都会变，Vue 会错误地复用节点，导致不必要的更新，甚至出现输入框内容错位的 bug。

### 51. ★★ `nextTick` 原理；`computed` 和 `watch` 的区别；`keep-alive` 原理。

**`nextTick`：**
- Vue 修改数据后不会立刻更新 DOM，而是把更新任务放进队列，同一轮里多次修改只更新一次（异步批量更新）。
- `nextTick` 把回调放到这次 DOM 更新之后执行，所以在回调里能拿到最新的 DOM。
- 实现上优先用微任务：Vue3 直接用 `Promise.then`；Vue2 按 `Promise.then` → `MutationObserver` → `setImmediate` → `setTimeout` 的顺序降级。

**`computed` 和 `watch`：**

| 对比项 | computed | watch |
| --- | --- | --- |
| 用途 | 根据已有数据算出一个新值 | 数据变化时执行副作用，比如发请求 |
| 缓存 | 有缓存，依赖不变就不重新计算 | 没有缓存 |
| 返回值 | 必须有返回值 | 不需要 |
| 异步 | 不适合放异步逻辑 | 可以写异步逻辑 |

**`keep-alive`：**
- 被包裹的组件切换走时不销毁，而是把组件实例（虚拟节点）存进缓存（用组件的 key 作为键）。
- 再次切回来时直接从缓存里取出复用，不重新创建，所以保留了状态。
- 生命周期上，切走触发 `deactivated`，切回来触发 `activated`。
- 用 `include` 和 `exclude` 控制缓存哪些组件；`max` 限制最多缓存几个，超出后按 **LRU（最近最少使用）** 规则淘汰最久没用的那个。

### 52. ★★ Composition API 相比 Options API 的好处；Pinia 和 Vuex 的区别。

**Composition API 的好处：**
1. **逻辑可以按功能组织**：Options API 里同一个功能的代码分散在 `data`、`methods`、`computed`、`watch` 里；Composition API 可以把一个功能的代码写在一起。
2. **逻辑复用更好**：可以抽成组合式函数（比如 `useTable`、`usePermission`），替代 Vue2 的 mixin。mixin 的问题是来源不清、容易命名冲突。
3. **TypeScript 支持更好**，类型推导更自然。
4. 对 Tree Shaking 更友好。

**Pinia 和 Vuex：**

| 对比项 | Pinia | Vuex |
| --- | --- | --- |
| 修改状态 | 没有 mutations，直接在 actions 里改，或直接修改状态 | 同步修改必须通过 mutations，异步放 actions |
| 模块 | 每个 store 独立定义，天然模块化 | 一个大 store 下用 modules 嵌套，要处理命名空间 |
| TypeScript | 支持很好，类型自动推导 | 支持较差 |
| 体积 | 很小 | 相对大 |
| 现状 | Vue 官方推荐 | Vue3 项目基本不再推荐 |

### React

### 53. ★★ Hooks 为什么不能写在条件语句里？`useEffect` 和 `useLayoutEffect` 的区别？

**为什么不能写在条件里：**
- React 不是按名字来记录每个 Hook 的，而是**按调用顺序**，把 Hook 的状态存在组件对应的 Fiber 节点上的一个链表里。
- 每次渲染时，React 按顺序依次取出第 1 个、第 2 个 Hook 的状态。
- 如果某个 Hook 写在 `if` 里，某次渲染没执行，后面所有 Hook 的顺序都会错位，取到的状态就乱了。

**`useEffect` 和 `useLayoutEffect`：**
- `useEffect`：在浏览器**绘制完成之后**异步执行，不阻塞页面显示。大多数副作用都用它，比如请求数据、订阅事件。
- `useLayoutEffect`：在 **DOM 更新之后、浏览器绘制之前**同步执行，会阻塞绘制。用于需要读取 DOM 尺寸并立刻修改的场景，比如测量元素宽度后调整位置，可以避免页面闪烁。

### 54. ★ Fiber 是什么，解决了什么问题？

- **之前的问题**：React 15 的更新是递归遍历整棵组件树，一旦开始就不能中断。组件树很大时会长时间占用主线程，导致动画卡顿、输入没反应。
- **Fiber 的做法**：
  - 把组件树改成链表结构的 Fiber 树，每个 Fiber 节点是一个工作单元。
  - 渲染工作可以被拆成很多小块，做一小块就检查一下有没有更高优先级的任务（比如用户输入）。有的话先暂停，把主线程让出去，之后再继续。这就是**时间切片**。
  - 不同的更新有不同的优先级（React 18 用 Lanes 模型），用户交互优先于数据加载。
- **两个阶段**：
  - render 阶段：计算哪些节点要变，可以中断。
  - commit 阶段：把变化真正应用到 DOM，不能中断。
- React 18 的并发特性（`useTransition`、`useDeferredValue`）就是建立在 Fiber 之上的。

### 55. ★★ Vue 和 React 的区别，你怎么选？

| 对比项 | Vue | React |
| --- | --- | --- |
| 更新机制 | 响应式，自动追踪依赖，精确知道哪个组件要更新 | 状态变化后默认重新渲染组件及其子组件，需要用 `memo` 等手动优化 |
| 写法 | 模板 + 指令，接近 HTML | JSX，所有东西都是 JS |
| 数据流 | 支持双向绑定 `v-model` | 单向数据流 |
| 生态 | 官方提供路由、状态管理，选择少但统一 | 社区方案多，灵活但需要自己选 |
| 上手难度 | 较低 | 需要理解更多概念，比如闭包陷阱、依赖数组 |

### JS 基础

### 56. ★★★ 事件循环：宏任务和微任务

**规则：**
1. JS 是单线程的，先执行同步代码。
2. 同步代码执行完后，**清空所有微任务**，包括执行过程中新产生的微任务。
3. 浏览器可能进行一次渲染。
4. 取出**一个**宏任务执行，然后回到第 2 步。

**分类：**
- 微任务：`Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`、`await` 之后的代码。
- 宏任务：`setTimeout`、`setInterval`、I/O、UI 事件、`MessageChannel`、整体的 `script`。

**常见题目：**

```js
console.log(1)
setTimeout(() => console.log(2), 0)
Promise.resolve().then(() => console.log(3))
async function fn() {
  console.log(4)
  await null
  console.log(5)
}
fn()
new Promise(resolve => {
  console.log(6)
  resolve()
}).then(() => console.log(7))
console.log(8)
```

**输出：1 4 6 8 3 5 7 2**

讲解：
- 同步代码依次输出 1、4、6、8。注意 `new Promise` 里的函数是同步执行的；`async` 函数里 `await` 之前的代码也是同步的。
- 微任务按加入顺序执行，输出 3、5、7。`await` 之后的代码相当于放进了 `then`。
- 最后执行宏任务 `setTimeout`，输出 2。

### 57. ★★ 原型链；`new` 做了什么；继承的几种方式。

**原型链：**
- 每个对象都有一个内部链接 `__proto__`，指向它的原型对象。
- 访问一个属性时，先在对象自身找，找不到就沿着 `__proto__` 往上找，直到 `Object.prototype`，再往上是 `null`。这条链就是原型链。
- 构造函数的 `prototype` 就是它创建出来的实例的原型：`实例.__proto__ === 构造函数.prototype`。

**`new` 做了什么：**
1. 创建一个空对象。
2. 把这个对象的原型指向构造函数的 `prototype`。
3. 以这个对象作为 `this` 执行构造函数。
4. 如果构造函数返回了一个对象，就用这个对象作为结果，否则返回第 1 步创建的对象。

```js
function myNew(Ctor, ...args) {
  const obj = Object.create(Ctor.prototype)
  const result = Ctor.apply(obj, args)
  return result !== null && (typeof result === 'object' || typeof result === 'function') ? result : obj
}
```

**继承方式：**
1. **原型链继承**：`Child.prototype = new Parent()`。问题是引用类型的属性会被所有实例共享，也不能给父类传参。
2. **构造函数继承**：在子类里 `Parent.call(this)`。问题是继承不到父类原型上的方法。
3. **组合继承**：前两种结合。问题是父类构造函数被调用了两次。
4. **寄生组合继承**：`Child.prototype = Object.create(Parent.prototype)` 加 `Parent.call(this)`，是 ES5 中最好的方式。
5. **ES6 `class extends`**：本质上是寄生组合继承的语法糖，现在都用这个。

### 58. ★★★ 手写 Promise、`Promise.all`、`Promise.race`

**Promise 的核心规则：**
- 三种状态：`pending`、`fulfilled`、`rejected`，状态一旦改变就不能再变。
- `then` 返回一个新的 Promise，所以可以链式调用。
- `then` 的回调要异步执行（微任务）。
- 回调返回的值如果是 Promise，要等它完成后再决定新 Promise 的状态。

```js
class MyPromise {
  constructor(executor) {
    this.state = 'pending'
    this.value = undefined
    this.callbacks = []

    const settle = (state, value) => {
      if (this.state !== 'pending') return
      this.state = state
      this.value = value
      this.callbacks.forEach(cb => cb())
    }
    const resolve = value => {
      if (value instanceof MyPromise) return value.then(resolve, reject)
      settle('fulfilled', value)
    }
    const reject = reason => settle('rejected', reason)

    try {
      executor(resolve, reject)
    } catch (err) {
      reject(err)
    }
  }

  then(onFulfilled, onRejected) {
    onFulfilled = typeof onFulfilled === 'function' ? onFulfilled : v => v
    onRejected = typeof onRejected === 'function' ? onRejected : e => { throw e }

    return new MyPromise((resolve, reject) => {
      const run = () => {
        queueMicrotask(() => {
          try {
            const handler = this.state === 'fulfilled' ? onFulfilled : onRejected
            const result = handler(this.value)
            result instanceof MyPromise ? result.then(resolve, reject) : resolve(result)
          } catch (err) {
            reject(err)
          }
        })
      }
      this.state === 'pending' ? this.callbacks.push(run) : run()
    })
  }

  catch(onRejected) {
    return this.then(null, onRejected)
  }
}
```

> 说明：完整的 Promise/A+ 规范还要处理 thenable 对象（带 `then` 方法的普通对象）和返回自身导致的循环引用，面试时可以口头补充。

**`Promise.all`：** 全部成功才成功，结果按传入顺序排列；任何一个失败就立即失败。

```js
function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    const list = Array.from(promises)
    const results = []
    let count = 0
    if (list.length === 0) return resolve(results)

    list.forEach((p, i) => {
      Promise.resolve(p).then(value => {
        results[i] = value
        if (++count === list.length) resolve(results)
      }, reject)
    })
  })
}
```

**`Promise.race`：** 谁先有结果（成功或失败）就用谁的。

```js
function promiseRace(promises) {
  return new Promise((resolve, reject) => {
    for (const p of promises) {
      Promise.resolve(p).then(resolve, reject)
    }
  })
}
```

> 顺带记住：`Promise.allSettled` 等所有都结束，返回每个的状态和结果；`Promise.any` 只要有一个成功就成功，全部失败才失败。

### 59. ★★ 手写题：防抖、节流、深拷贝、LRU 缓存

**防抖**：连续触发时，只在最后一次触发后等待一段时间再执行。适合搜索框输入。

```js
function debounce(fn, delay) {
  let timer = null
  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => fn.apply(this, args), delay)
  }
}
```

**节流**：一段时间内最多执行一次。适合滚动、窗口缩放。

```js
function throttle(fn, interval) {
  let last = 0
  return function (...args) {
    const now = Date.now()
    if (now - last >= interval) {
      last = now
      fn.apply(this, args)
    }
  }
}
```

**深拷贝**：要处理循环引用、数组、日期、正则等。

```js
function deepClone(value, map = new WeakMap()) {
  if (value === null || typeof value !== 'object') return value
  if (value instanceof Date) return new Date(value)
  if (value instanceof RegExp) return new RegExp(value)
  if (map.has(value)) return map.get(value)

  const copy = Array.isArray(value) ? [] : {}
  map.set(value, copy)
  for (const key of Reflect.ownKeys(value)) {
    copy[key] = deepClone(value[key], map)
  }
  return copy
}
```

> 顺带说一下：现代浏览器可以直接用 `structuredClone`，但它不能拷贝函数。`JSON.parse(JSON.stringify())` 会丢失函数、`undefined`、日期类型，遇到循环引用会报错。

**LRU 缓存**：容量满了以后，淘汰最久没被使用的数据。利用 `Map` 会按插入顺序保存键的特点。

```js
class LRUCache {
  constructor(capacity) {
    this.capacity = capacity
    this.map = new Map()
  }

  get(key) {
    if (!this.map.has(key)) return -1
    const value = this.map.get(key)
    this.map.delete(key)
    this.map.set(key, value)
    return value
  }

  put(key, value) {
    if (this.map.has(key)) this.map.delete(key)
    this.map.set(key, value)
    if (this.map.size > this.capacity) {
      this.map.delete(this.map.keys().next().value)
    }
  }
}
```

> 讲解：每次访问就把这个键删掉再重新插入，它就变成“最新”的；`Map` 的第一个键就是最久没用的，满了就删它。`keep-alive` 的 `max` 也是这个原理。

### 浏览器与网络

### 60. ★★★ 浏览器渲染流程；回流和重绘；怎么减少回流

**渲染流程：**
1. 解析 HTML，生成 **DOM 树**。
2. 解析 CSS，生成 **CSSOM 树**。
3. 两者结合生成**渲染树**（不包含 `display: none` 的元素）。
4. **布局（Layout）**：计算每个元素的位置和大小。
5. **绘制（Paint）**：把元素画成像素，分成多个图层。
6. **合成（Composite）**：把各个图层合成最终画面显示出来。

**回流和重绘：**
- **回流（重排）**：元素的位置、大小、结构发生变化，需要重新计算布局。比如修改宽高、增删元素、改字体大小，或者读取 `offsetWidth`、`getBoundingClientRect` 等布局属性。
- **重绘**：只是外观变化，不影响布局，比如改颜色、背景色。
- **回流一定会引起重绘，重绘不一定引起回流。** 回流的代价更大。

**减少回流的方法：**
1. 批量修改样式：用切换 class 代替逐条修改 `style`。
2. 批量操作 DOM：用 `DocumentFragment`，或者先把元素隐藏、改完再显示。
3. 不要在循环里交替读写布局属性，先统一读，再统一写，否则会强制浏览器反复同步计算布局。
4. 动画用 `transform` 和 `opacity`：它们只在合成阶段处理，不触发回流和重绘，还可以用 GPU 加速。
5. 频繁变化的元素用 `will-change` 或绝对定位，让它脱离文档流，减少影响范围。
6. 长列表用虚拟滚动，减少 DOM 数量。

### 61. ★★★ HTTP 缓存：强缓存和协商缓存

**强缓存**：在有效期内，浏览器直接用本地缓存，**不发请求**。
- `Cache-Control: max-age=31536000`：缓存的有效秒数（HTTP/1.1，优先级更高）。
- `Expires`：过期的具体时间（HTTP/1.0，依赖客户端时间，可能不准）。
- `Cache-Control` 的其他常见值：
  - `no-cache`：可以缓存，但每次都要先问服务器（走协商缓存）。
  - `no-store`：完全不缓存。
  - `immutable`：资源永远不会变，有效期内连刷新都不重新验证。

**协商缓存**：强缓存过期后，浏览器带着标识去问服务器资源有没有变。没变返回 **304**，浏览器继续用本地缓存；变了返回 200 和新内容。
- `ETag` / `If-None-Match`：根据内容生成的标识，内容变了它就变，更精确，优先级更高。
- `Last-Modified` / `If-Modified-Since`：最后修改时间，只精确到秒；而且文件内容没变、只是修改时间变了，也会被判定为更新。

**前端项目的最佳实践：**
- `index.html`：设置 `no-cache`，每次都确认是否有新版本，保证用户能拿到最新的入口。
- 带 hash 的 JS 和 CSS 文件（比如 `app.3f2a1b.js`）：设置很长的 `max-age` 加 `immutable`。内容一变文件名就变，所以可以放心长期缓存。

### 62. ★★ HTTPS 握手；HTTP/2 的改进；TCP 三次握手和四次挥手

**HTTPS 握手（TLS 1.2，ECDHE 方式）：**
1. 客户端发送 ClientHello：支持的 TLS 版本、加密套件列表、一个随机数。
2. 服务端回复 ServerHello：选定的加密套件、一个随机数，并发送**证书**和密钥交换参数。
3. 客户端**验证证书**：是否由可信的 CA 签发、是否过期、域名是否匹配。
4. 双方通过密钥交换算法（ECDHE），各自算出相同的**会话密钥**，密钥本身不在网络上传输。
5. 双方发送 Finished 消息确认，之后用会话密钥进行对称加密通信。

> 要点：**用非对称加密安全地协商出密钥，再用对称加密传输数据**，因为对称加密速度快。TLS 1.3 把握手简化到 1 个往返（1-RTT），更快。

**HTTP/2 相比 HTTP/1.1 的改进：**
1. **二进制分帧**：数据被拆成二进制帧传输，解析更高效。
2. **多路复用**：一个 TCP 连接上可以同时传输多个请求和响应，解决了 HTTP/1.1 的队头阻塞问题（HTTP/1.1 里前一个请求没响应，后面的就得等）。所以 HTTP/1.1 时代的“合并文件”“雪碧图”“域名分片”等优化，在 HTTP/2 下就不那么必要了。
3. **头部压缩（HPACK）**：重复的请求头不用每次都完整发送。
4. **服务器推送**：现在基本不用了，主流浏览器已经移除支持。
5. **仍然存在的问题**：TCP 层丢包时，所有流都要等待重传，还是有队头阻塞。HTTP/3 改用基于 UDP 的 QUIC 协议来解决这个问题。

**TCP 三次握手：**
1. 客户端发送 SYN：“我想建立连接。”
2. 服务端回复 SYN + ACK：“收到，我也想建立连接。”
3. 客户端回复 ACK：“收到。”

> **为什么是三次**：要确认双方的发送和接收能力都正常。两次的话，服务端不知道客户端能不能收到自己的消息；另外还能防止网络里滞留的旧连接请求突然到达，导致服务端错误地建立连接。

**TCP 四次挥手：**
1. 客户端发送 FIN：“我没有数据要发了。”
2. 服务端回复 ACK：“知道了。”（但服务端可能还有数据没发完，继续发送。）
3. 服务端发送 FIN：“我也发完了。”
4. 客户端回复 ACK，然后等待 **2MSL**（报文最大生存时间的两倍）再关闭。

> **为什么是四次**：因为 TCP 是全双工的，两个方向要分别关闭，服务端的 ACK 和 FIN 往往不能合并发送。**为什么要等 2MSL**：确保最后一个 ACK 能到达服务端（如果丢了，服务端会重发 FIN），也让本次连接的旧报文在网络中全部消失。

### 63. ★ 跨域的解决方案；XSS 和 CSRF 怎么防

**跨域：** 浏览器的同源策略要求协议、域名、端口都相同，否则不能读取接口返回的内容。

解决方案：
1. **CORS**（最主流）：服务端返回 `Access-Control-Allow-Origin` 等响应头。非简单请求（比如带自定义请求头、`Content-Type: application/json`）会先发一个 `OPTIONS` 预检请求。
2. **代理**：开发环境用 Vite 或 Webpack 的 `devServer.proxy`，生产环境用 Nginx 反向代理。服务器之间请求没有同源限制。
3. **postMessage**：用于不同窗口、iframe 之间的通信。
4. **JSONP**：利用 `<script>` 标签不受同源限制，只支持 GET，现在基本不用了。

**XSS（跨站脚本攻击）：** 攻击者把恶意脚本注入页面，在其他用户的浏览器里执行，从而窃取 Cookie、冒充用户操作。

防范：
- 对用户输入的内容做转义后再输出。Vue 的 `{{ }}` 和 React 的 JSX 默认会转义。
- 慎用 `v-html`、`innerHTML`、`dangerouslySetInnerHTML`；必须用时，先用 DOMPurify 过滤。
- 设置 CSP（内容安全策略），限制页面只能加载可信来源的脚本。
- 敏感 Cookie 设置 `HttpOnly`，让 JS 读不到。

**CSRF（跨站请求伪造）：** 用户登录了 A 网站，又访问了恶意网站 B。B 偷偷向 A 发请求，浏览器会自动带上 A 的 Cookie，于是请求以用户的身份执行。

防范：
- Cookie 设置 `SameSite=Lax` 或 `Strict`，限制跨站请求携带 Cookie。
- 使用 CSRF Token：服务端生成随机 token，请求时放在请求头或表单里，恶意网站拿不到。
- 服务端校验 `Origin` 或 `Referer` 请求头。
- 用 `Authorization` 请求头传 token，而不是用 Cookie，就天然不受 CSRF 影响。

### 工程化

### 64. ★★★ Vite 为什么开发环境快？和 Webpack 原理上有什么区别？

**Webpack 开发环境：** 启动时要从入口开始，分析整个项目的依赖，把所有模块**打包**后才能启动服务。项目越大，启动越慢；改一个文件，也要重新构建相关的模块链。

**Vite 开发环境快的原因：**
1. **不打包，按需编译**：利用浏览器原生支持的 ES Module（`<script type="module">`），启动时不打包。浏览器请求哪个文件，Vite 才编译哪个文件，所以启动时间基本不受项目大小影响。
2. **依赖预构建**：`node_modules` 里的第三方依赖用 esbuild（Go 语言编写，比 JS 写的工具快几十倍）预先打包成 ESM 格式并缓存。这样既解决了部分库是 CommonJS 格式的问题，又避免了像 lodash-es 这种包导致浏览器发出几百个请求。
3. **HMR 更快**：改了一个文件，只需要让这个模块失效并重新请求，速度和项目大小无关。
4. **利用浏览器缓存**：依赖用强缓存，源码用协商缓存。

**生产环境：** Vite 仍然要打包，因为大量的 ES Module 请求在生产环境性能不好。生产构建用的是 Rollup，新版本正在逐步切换到 Rust 编写的 Rolldown。

**一句话总结**：Webpack 是“先打包再启动”，Vite 是“先启动，浏览器要什么再编译什么”。

### 65. ★★ Webpack 的 loader 和 plugin 区别；Tree Shaking 原理

**loader 和 plugin：**
- **loader**：文件转换器。Webpack 本身只认识 JS 和 JSON，loader 把其他类型的文件转换成 Webpack 能处理的模块。比如 `babel-loader` 转换新语法，`css-loader` 处理 CSS 里的依赖，`vue-loader` 处理 `.vue` 文件。loader 的执行顺序是从右往左、从下往上。
- **plugin**：扩展器。Webpack 在构建过程中会在各个阶段广播事件（基于 Tapable 钩子），plugin 监听这些钩子，在特定阶段做事。比如 `HtmlWebpackPlugin` 生成 HTML，`MiniCssExtractPlugin` 把 CSS 抽成单独的文件，`DefinePlugin` 注入环境变量。
- **区别**：loader 只负责**转换某类文件**；plugin 能介入**整个构建流程**，能力更广。

**Tree Shaking：** 把代码里没被用到的导出删掉。

原理：
1. 依赖 **ES Module 的静态结构**：`import` 和 `export` 只能写在顶层，不能放在条件语句里，所以在编译阶段（不运行代码）就能确定哪些导出被用到了。CommonJS 的 `require` 是运行时动态执行的，无法做 Tree Shaking。
2. 打包工具先**标记**没被使用的导出，再由压缩工具（Terser）真正**删除**这些代码。
3. **副作用**：有些模块被导入时就会执行代码（比如修改全局对象、引入 CSS），即使没用它的导出也不能删。在 `package.json` 里配置 `sideEffects: false` 或列出有副作用的文件，告诉打包工具哪些可以放心删除。

> 注意：Babel 不要把 ES Module 转成 CommonJS，否则 Tree Shaking 会失效。

### 66. ★ TypeScript：泛型、常用工具类型

**泛型**：在定义函数、接口时不先确定具体类型，等使用时再指定，类似于类型的“参数”。

```ts
interface ApiResponse<T> {
  code: number
  message: string
  data: T
}

function request<T>(url: string): Promise<ApiResponse<T>> {
  return fetch(url).then(res => res.json())
}

// 使用时指定 data 的类型
const res = await request<User[]>('/api/users')
```

> 泛型约束：`function getLength<T extends { length: number }>(arg: T)`，表示 T 必须有 `length` 属性。

**常用工具类型：**

| 工具类型 | 作用 | 示例 |
| --- | --- | --- |
| `Partial<T>` | 所有属性变成可选 | 编辑表单的部分字段 |
| `Required<T>` | 所有属性变成必填 | |
| `Readonly<T>` | 所有属性变成只读 | |
| `Pick<T, K>` | 只挑选部分属性 | `Pick<User, 'id' \| 'name'>` |
| `Omit<T, K>` | 去掉部分属性 | `Omit<User, 'password'>` |
| `Record<K, V>` | 构造一个键类型为 K、值类型为 V 的对象 | `Record<string, number>` |
| `ReturnType<F>` | 获取函数的返回值类型 | |
| `Parameters<F>` | 获取函数参数类型组成的元组 | |

> 可以顺带说一下 `Partial` 的实现原理，用的是映射类型：`type Partial<T> = { [K in keyof T]?: T[K] }`。

```js
function arrayToTree(list, rootId = 0) {
  const map = new Map()
  const roots = []
  list.forEach(item => map.set(item.id, { ...item, children: [] }))
  map.forEach(node => {
    const parent = map.get(node.parentId)
    if (node.parentId === rootId || !parent) roots.push(node)
    else parent.children.push(node)
  })
  return roots
}
```

## 八、京东供应链业务

### 68. ★★ 你理解的供应链包括哪些环节？

> 简单说，供应链就是“商品从供应商到消费者手里”的全过程：
>
> 1. **计划**：根据历史销量做销量预测，决定要备多少货。
> 2. **采购**：向供应商下采购单，涉及价格谈判、合同、审批。
> 3. **入库**：货到仓库后验收、上架，生成入库单，库存增加。
> 4. **库存管理**：实时库存、库存调拨（在不同仓库之间调货）、盘点、补货、滞销和缺货预警。
> 5. **销售和订单**：用户下单后，占用库存。
> 6. **出库和履约**：拣货、打包、出库，交给物流配送；京东的“211 限时达”就是履约能力的体现。
> 7. **逆向物流**：退货、换货、退供应商。
> 8. **结算和对账**：和供应商、平台、物流公司结算。
>
> 对应的系统大概有采购系统、WMS（仓储管理系统）、库存系统、OMS（订单管理系统）、TMS（运输管理系统）、结算系统等。
>
> 前端上，这些系统的共同特点是：**大量的复杂表格和表单、单据状态多、权限细、数据量大、对准确性要求高**。这和我做过的慧经营报表、四级权限、单据状态机、CRUD 配置化都很匹配。

### 69. ★ 如果让你做一个采购单管理页，你会怎么设计？

> 我会从这几个方面考虑：
>
> 1. **列表页**：用 CRUD 配置化组件，搜索条件包括单号、供应商、状态、创建时间；表格展示单号、供应商、金额、状态、创建人；操作按钮根据单据状态和用户权限动态显示。
> 2. **状态流转**：用状态机配置管理“草稿 → 待审核 → 已审核 → 部分入库 → 全部入库 / 已驳回 / 已作废”，每个状态允许哪些操作写在配置里。
> 3. **新建和编辑页**：基本信息表单加商品明细表格。商品明细支持远程搜索选择商品、批量录入、从 Excel 粘贴导入；数量和单价变化时自动计算小计和总金额（金额计算要注意精度）；提交前做完整校验。
> 4. **详情页**：展示单据信息、商品明细，以及操作日志或审批流时间线，方便追溯。
> 5. **性能**：明细行多的时候用虚拟滚动；列表数据量大时做分页和导出。
> 6. **防重复提交**：提交按钮加 loading 和防抖，后端接口做幂等处理。
> 7. **权限**：菜单、按钮、数据权限，比如采购员只能看到自己负责的供应商。
